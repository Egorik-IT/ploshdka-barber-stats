# Запуск для одной организации

Приложение рассчитано на один процесс Node.js и одну базу PostgreSQL. Очередь YCLIENTS, ограничение попыток входа и выполняющиеся задания находятся в памяти процесса. Несколько процессов без общего хранилища этих состояний пока не поддерживаются.

## Перед обновлением

1. Выполнить `npm run db:backup`. Нужен установленный `pg_dump` совместимой с сервером PostgreSQL версии. При необходимости задать `PG_DUMP_PATH`.
2. Скопировать архив в защищённое хранилище вне сервера приложения. Архив содержит персональные данные; не публиковать его и не класть в `dist`.
3. Проверить восстановление командой `npm run db:verify-backup -- backups/имя.dump`. Проверка создаёт случайную отдельную базу, восстанавливает архив, читает основные таблицы и удаляет тестовую базу. Нужен пользователь PostgreSQL с правом CREATEDB; рабочему пользователю приложения это право для эксплуатации не требуется. Проверять с отдельными реквизитами через переменные окружения. Рабочая база не является целью восстановления.

Успешное создание архива само по себе не подтверждает возможность восстановления. Если отдельную базу создать нельзя, проверку должен выполнить администратор PostgreSQL на тестовом сервере. Не подменять её восстановлением поверх рабочей базы.

## Установка и запуск

1. Установить зависимости: `npm ci`.
2. Заполнить `.env` по `.env.example`. Секреты не передавать в переменных с префиксом `VITE_`: такие значения могут попасть в браузер.
3. Выполнить `npm run db:migrate`, затем `npm run lint`, `npm test`, `npm run build`.
4. Для дополнительных проверок БД задать `RUN_DB_TESTS=1` и запустить `npm test`. Эти проверки используют изолированные тестовые данные.
5. В production задать `NODE_ENV=production`, точный HTTPS-адрес в `APP_ORIGINS` без завершающего слеша и случайный `SESSION_SECRET` длиной не менее 32 символов.
6. Запустить `npm start` под системной службой с автоматическим перезапуском. Сервер раздаёт собранный `dist` и `/api` с одного адреса.
7. Настроить HTTPS-прокси. Приложение по умолчанию слушает только `127.0.0.1:3001`; не открывать этот порт и PostgreSQL в интернет. Для локального прокси задать `TRUST_PROXY=loopback`. Не доверять произвольным внешним proxy-заголовкам.

Пример конфигурации Caddy (заменить домен своим, настроить DNS):

```text
stats.example.com {
    reverse_proxy 127.0.0.1:3001
}
```

После запуска проверить `/api/health`, `/api/health/db`, вход, выход, обновление страницы на вложенном маршруте и работу каждой роли. Сессия в production использует Secure/HttpOnly/SameSite=Lax cookie, поэтому вход через обычный HTTP работать не должен. Проверки API берут актуальную роль из БД; роль в браузере управляет только отображением.

## Эксплуатация и границы проверки

- Планировщик сервера должен регулярно запускать резервное копирование. Автоматическое расписание и внешнее хранилище самим приложением не настраиваются.
- Изменяющие API-запросы записываются в `audit_events` без тела запроса и секретов. Запись выполняется после ответа, отдельно от бизнес-транзакции: это эксплуатационный журнал, а не гарантированный бухгалтерский аудит.
- Отчёты показывают время использованного снимка. Обычный кэш и история клиентов имеют разные сроки актуальности. После перезапуска незавершённую синхронизацию нужно запустить повторно; уже сохранённые страницы истории могут использоваться повторно.
- Ставки применяются из текущих настроек. Истории ставок с датой вступления в силу пока нет; изменение ставки может изменить перерасчёт старого периода.
- Ручные выплаты и расходы сохраняются для выбранного филиала и точного периода. Это не реестр отдельных выплат и не бухгалтерский учёт.
- Публикация в маркете YCLIENTS и работа нескольких организаций требуют отдельной реализации подключения и изоляции организаций.
